当前站点基线

这不是通用的“Hello World”，而是当前博客所用 Markdown 与公式渲染链路的可复现说明。写作时项目配置为：

  • Hexo 7.3.0；
  • hexo-renderer-pandoc ^0.4.0；
  • hexo-filter-mathjax ^0.9.0；
  • mathjax-full ^3.2.2；
  • hexo-server ^3.0.0；
  • hexo-deployer-git ^4.0.0。

安装项目依赖

仓库已经有 lockfile 时，优先使用可复现安装：

npm ci 会按 package-lock.json 重建 node_modules。不要手工修改 node_modules：其中的改动不会成为可靠配置，下次安装依赖就会丢失。

当前项目没有同时声明 hexo-renderer-marked，因此 .md 文件由 Pandoc renderer 处理。不要同时安装多个争抢同一扩展名的 Markdown renderer。

Pandoc 是独立的系统程序

hexo-renderer-pandoc 只是调用器，不会把 Pandoc 可执行文件打包进 npm 依赖。Hexo 构建时必须能从 PATH 找到 pandoc。

发行版仓库中的 Pandoc 可能不是最新版；只有确实需要新语法或修复时，才从 Pandoc 官方发布页安装对应平台包。

如果 Terminal 能找到 Pandoc，但由 IDE、LaunchAgent 或 CI 启动的 Hexo 找不到，通常是进程 PATH 不同。应修正启动环境；也可以把 command -v pandoc 得到的绝对路径配置为 pandoc.pandoc_path。不要复制别人的 /opt/homebrew/bin/pandoc，Intel Mac、Apple Silicon 和其他系统的路径可能不同。

wrap: none 的真实作用

当前 _config.yml 使用 renderer 0.4.0 仍然支持的旧字典兼容接口：

它会把配置转换为 Pandoc 参数 --wrap none。该参数控制的是 Pandoc 生成的 HTML 源码如何换行，不是浏览器中的段落排版，也不会修复 Markdown 中人为插入的硬换行。

旧做法常让人直接编辑 node_modules/hexo-renderer-pandoc/lib/parseArgs.js。这既不可复现，也会在 npm ci 后消失；当前 _config.yml 已经能够表达相同意图，不应修改依赖源码。

renderer 0.4.0 的 README 已优先推荐 pandoc.args，但只要出现 args，插件就不再自动补上旧接口默认使用的输入格式、输出格式和 --mathjax 等参数。因此不能只把当前配置机械改成 args: ["--wrap", "none"]，否则会改变渲染链路。当前 extra 配置仍可用；以后迁移或升级时，应按对应版本 README 写出完整参数，并执行公式、代码块和 Hexo 标签的回归构建。

MathJax 的处理链路

当前链路分为两步：

  1. Pandoc 把 Markdown 数学语法转换为带 \(...\) 或 \[...\] 定界符的 HTML；
  2. hexo-filter-mathjax 使用本地 mathjax-full 在构建期生成 SVG MathJax 标记。

这是服务端构建期渲染，不依赖页面运行时再从 CDN 下载 MathJax。主题若还启用了另一套前端 KaTeX/MathJax，应关闭其中一套，避免公式被重复处理。

单美元符号的风险

当前配置为 single_dollars: true，因此 $...$ 也会被 MathJax 当成行内公式。它写公式很方便，但普通文本中的成对货币符号可能被误解析，例如两个价格之间的整段文字。

在这套 Pandoc 链路中，行内公式应紧贴定界符书写：

不要写成 $ E=mc^2 $。包含大量美元金额的文章，可以把字面金额放在代码片段中，例如 `$100`；更彻底的方案是把站点配置改为 single_dollars: false 后执行完整回归构建。仅在 Markdown 中写 \$ 未必足够，因为 Pandoc 可能先去掉转义，后续过滤器仍会看到美元符号。

Hexo 四个常用命令的区别

当前 package.json 已提供 clean、build、server、deploy 四个脚本。

npm run clean

对应 hexo clean，删除 Hexo 缓存数据库 db.json 和生成目录 public/。它不会删除 source/ 中的文章。插件、主题或配置变化后出现旧内容时，先 clean 再构建。

npm run build

对应 hexo generate，读取站点配置和 source/，把静态文件写入 public/。它不启动服务器，也不部署：

npm run server

对应 hexo server，启动本地预览和文件监听，默认地址通常为 http://localhost:4000/：

端口占用时可直接调用 Hexo 并指定端口：

本地预览正常不代表部署目标、域名基础路径和 CI 环境一定正常。

npm run deploy

对应 hexo deploy，调用 _config.yml 中配置的 deployer，把已有产物发送到远端。它是外部写操作，执行前必须确认目标仓库、分支、凭据和 public/ 内容：

deploy 不应被当成普通构建命令。稳妥流程是先显式清理、生成和本地检查，再单独部署：

Hexo 也支持 hexo deploy --generate，但拆开执行更容易确认究竟是渲染失败还是部署失败。

完整验证流程

1. 检查工具链

如果出现 pandoc exited with code ...、找不到命令或退出码为空，先单独运行 pandoc --version，再检查启动 Hexo 的进程是否继承了正确 PATH。

2. 从干净状态生成

构建必须以退出码 0 结束。警告也应阅读，不要只检查是否产生了 public/。

3. 检查本篇产物

当前 permalink 规则包含日期与文件名，所以本篇通常生成到：

可做静态搜索：

预期同时找到 MathJax 的 mjx-container 和代码测试字符串。然后启动本地服务器，肉眼确认：

  • 行内公式和块级公式都已排版；
  • 中文前后没有异常断行；
  • 代码块保留高亮、空格和反斜杠；
  • 页面控制台没有重复 MathJax、资源 404 或脚本异常。

4. 只在确认后部署

先检查生成目录、Git 目标和本地页面，再执行部署。构建验证不需要、也不应该自动触发远端写入。

常见问题

公式源码原样显示

依次确认：

  1. 文章 front matter 是 mathjax: true；
  2. hexo-filter-mathjax 和 mathjax-full 已安装；
  3. Pandoc 成功处理该 Markdown；
  4. 主题没有转义、删除或二次渲染公式节点；
  5. clean 后重新 generate，而不是继续查看旧缓存。

所有文章构建都很慢

当前 every_page: false 已避免对无公式页面运行 MathJax。无公式文章不要无条件设置 mathjax: true。

Pandoc 输出换行不符合预期

确认 _config.yml 中是 renderer 0.4.0 支持的 extra 结构，并检查最终传参。不要修改 parseArgs.js。--wrap=none 只影响输出源码，页面中的视觉换行应由 HTML 结构和 CSS 控制。

本地成功、CI 失败

最常见原因是 CI 只安装了 Node.js，却没有安装 Pandoc，或者 Pandoc 版本和 PATH 不同。CI 中应显式安装 Pandoc，并输出 pandoc --version 作为诊断信息。
