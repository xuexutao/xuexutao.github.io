使用场景与最终目标

本文面向这样的本地开发环境：

  • 宿主机是 Windows 或 macOS；
  • VMware Workstation/Fusion 中运行 Ubuntu；
  • 宿主机通过 OpenSSH 登录虚拟机，并使用 SCP 双向传输文件。

完成后应能从宿主机执行 ssh 和 scp，无需在虚拟机中开启不必要的共享目录，也不需要把 SSH 暴露到公网。

文中的 YOUR_VM_USER、YOUR_VM_IP、YOUR_HOST_PORT 都是占位值，必须替换成自己的用户名、虚拟机地址和端口。不要把示例地址当成真实配置。

先选对 VMware 网络模式

SSH 能否连接，首先取决于宿主机和虚拟机之间是否有可达的 IP 路径。切换虚拟网卡模式前，建议先正常关闭虚拟机。

NAT

NAT 通常是笔记本开发环境的首选：

  • 虚拟机位于 VMware 创建的私有网段，并借用宿主机连接外网；
  • 宿主机通常可以直接访问虚拟机的私有 IP；
  • 局域网里的其他机器默认不能主动连接该虚拟机。

因此，宿主机连接 NAT 虚拟机时通常不需要端口转发，直接连接虚拟机 IP 的 22 端口即可。只有外部机器需要经宿主机进入 NAT 虚拟机，或当前 VMware 网络配置无法直接路由时，才考虑端口转发。

桥接

桥接模式让虚拟机像局域网中的独立设备一样，从物理网络获得地址：

  • 宿主机和局域网内其他设备可直接访问虚拟机；
  • 虚拟机会暴露在与宿主机相同的网络中，防火墙和账号安全更重要；
  • 企业 Wi-Fi、访客网络、无线 AP 隔离或网络准入策略可能禁止额外设备，导致桥接无法获取地址。

需要让局域网中的多台可信设备访问虚拟机时再使用桥接；只在本机开发时，NAT 的暴露面更小。

常见故障排查

连接超时

通常是 IP、网络模式、路由或防火墙问题：

  1. 在 Ubuntu 重新确认当前 IP，而不是沿用 DHCP 变化前的地址；
  2. 确认 VMware 网卡已连接，NAT/桥接模式符合预期；
  3. 从宿主机测试 TCP 22，而不是只依赖 ping；
  4. 检查 Ubuntu UFW、宿主机防火墙和企业网络策略；
  5. 使用端口转发时，确认映射仍指向当前虚拟机 IP。

安全检查清单

  • 不允许 root 直接登录，不共享私钥，不把私钥放入项目仓库；
  • 私钥使用口令，并优先交给系统的 SSH Agent 管理；
  • 桥接或端口转发时，只向必要的可信来源开放端口；
  • 不把更换 SSH 端口当成核心防护；
  • 定期安装 Ubuntu 安全更新，并移除不再使用的公钥；
  • 修改 SSH 和防火墙前保留 VMware 控制台与现有会话；
  • 不使用 chmod 777、关闭主机密钥校验或开放空密码来绕过问题。
