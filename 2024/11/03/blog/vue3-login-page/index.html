教程目标与版本

本文从空目录搭建一个前后一致的登录示例，包含：

  • Vue 单文件组件（SFC）；
  • Vue Router 4 的根路由、嵌套路由、Layout 和 <RouterView>；
  • Element Plus 表单与异步校验；
  • 可在组件卸载时清理的短信验证码倒计时；
  • Axios 实例、Bearer Token、超时、网络错误和 401 处理；
  • Vite 环境变量和 public 静态资源的正确路径。

示例固定主版本为 Vue 3、Vite 7、Vue Router 4、Element Plus 2、Axios 1，使用 Node.js 22.12 或更高的 22.x 版本。不要把旧的 Vue 2、Vue Router 3 或 Vue CLI 配置混进来。

本文使用 JavaScript，便于集中说明登录流程。生产项目可以改用 TypeScript，但接口约定和安全边界不变。

配置 API 基础地址

在项目根目录创建 .env：

/api 是同源占位路径。本地没有配置后端或 Vite 代理时，请求只会发给本机开发服务器并失败，不会把手机号、密码或 token 发往未知外部站点。接入时应把它指向自己控制的后端，优先通过同源反向代理提供 /api；若改用独立的 HTTPS API 域名，还要由后端正确配置 CORS。

只有以 VITE_ 开头的变量会暴露给浏览器。因此这里可以放公开的 API 地址，不能放数据库密码、私钥、短信服务密钥或其他秘密。Vite 在启动时加载 .env，并在构建时把这些值写入前端产物；修改后应重启开发服务器或重新构建，不能把它当成运行时秘密配置。

本文约定后端接口如下：

  • POST /auth/code：请求短信验证码，请求体为 { "phone": "..." }，任意 2xx 表示受理；
  • POST /auth/login：提交手机号、密码和 6 位短信码，成功返回 { "accessToken": "...", "user": { ... } }；
  • 受保护接口在凭据无效或过期时返回 HTTP 401。

短信发送频率限制、验证码校验、密码校验和账号锁定必须由后端完成。前端校验只改善交互，不能构成安全边界。

封装 Axios 请求

src/utils/request.js

公开接口通过自定义的 skipAuth 标记跳过 token，避免用容易遗漏的 URL 白名单。若项目改为 TypeScript，应扩展 Axios 请求配置类型，声明该字段。

响应拦截器只对受保护请求的 401 清理登录状态并跳转；登录和验证码接口带有 skipAuth，其 401 留给当前页面展示，避免用户离开登录页后旧请求又触发全局跳转。拦截器不弹出消息，具体页面捕获异常并展示一次，避免“拦截器提示一次、组件又提示一次”。代码不会打印 token、密码或完整请求体。

实现登录表单

src/views/LoginView.vue

这里修正了几类常见问题：

  • Element Plus 规则字段是 trigger，不是 triggle；
  • 正则使用 ^ 和 $ 完整锚定，手机号采用稳定的 ^1[3-9]\d{9}$，不硬编码容易过时的细分号段；
  • 密码登录只校验非空和合理长度，不用前端正则擅自拒绝后端已经允许的特殊字符；
  • setInterval 的句柄会在倒计时结束和组件卸载时清理，不会重复创建或继续修改已卸载组件；
  • 验证码和登录按钮在异步表单校验前就进入忙碌状态，避免快速重复点击发出并发请求；
  • 本页的异步登录或验证码请求在组件卸载后即使才返回，也不会再启动计时器、写入 token、跳转或弹出消息；
  • 只有验证码请求成功后才开始倒计时；
  • 表单通过原生 submit 流程触发，按 Enter 与点击按钮行为一致；
  • 跳转参数只接受站内绝对路径，避免开放重定向；
  • Element Plus Card 的类名是 .el-card__header，不是 .el-card_header。

本地运行与验证

启动开发服务器：

浏览器访问终端输出的地址，并依次检查：

  1. /login 能显示表单和 public/vite.svg；
  2. 空表单、错误手机号和非 6 位验证码会显示校验消息；
  3. 快速重复点击验证码或登录按钮不会发出并发请求；
  4. 离开登录页后计时器被清理；
  5. 未登录访问 / 会跳转到 /login?redirect=/；
  6. 接入受保护接口后，其 401 会清除 token 并返回登录页，而登录接口自己的 401 只显示一次错误；
  7. 控制台和网络日志中没有主动打印密码或 token。

默认的同源 /api 没有对应后端，所以发送验证码和登录请求失败是预期结果，且不会向外部 API 发送凭据。接入自己控制的测试后端后，再验证成功分支、401、429、超时、断网和畸形响应。

token 存储与生产安全

示例使用 localStorage 是为了清楚展示 Bearer Token 流程，但它有明确风险：同源页面中的 JavaScript 都能读取 token，一旦发生 XSS，凭据可能被窃取。生产系统通常应优先考虑由后端设置的 HttpOnly、Secure、合适 SameSite 属性的 Cookie，并配套 CSRF 防护。

如果业务必须使用 localStorage：

  • 使用短生命周期 access token 和可撤销的刷新机制；
  • 严格防止 XSS，设置 CSP，避免不可信 HTML 注入；
  • 不在日志、错误上报、URL、埋点或截图中输出 token；
  • 退出时清理凭据，401 时终止受保护状态；
  • 所有权限判断仍在服务端执行；
  • 短信接口在服务端限流，并避免通过错误消息泄露账号是否存在。

环境变量、前端路由守卫和隐藏按钮都不能保存秘密，也不能替代后端授权。
