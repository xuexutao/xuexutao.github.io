什么时候需要扩展

先确认瓶颈再写扩展。下列情况通常值得进入 C++/CUDA：

  • 算法包含 PyTorch 没有的算子或特殊数据结构；
  • 多个小算子之间产生了明显的 Python 调度和中间张量开销；
  • 需要调用已有的 C++/CUDA 库；
  • profiling 已确认热点在可自定义的 kernel，而不是数据加载、同步或模型其他部分。

如果需求能用现有 PyTorch 算子清晰表达，先保留 Python 实现：它天然支持 autograd、设备分派、混合精度和 torch.compile，维护成本也更低。

本文主线使用 torch.utils.cpp_extension.load_inline 构建一个 CPU 自定义算子。这样所有源代码都在一个 Python 文件中，适合验证最小闭环。需要打 wheel、供多人安装或接入 CI 时，再迁移到 setuptools/CppExtension。

环境准备

CPU 路径需要：

  • 已安装的 PyTorch；
  • 与当前 PyTorch 二进制兼容的 C++ 编译器；
  • Ninja（本文使用的 load_inline JIT 构建路径需要它）；
  • macOS 上的 Xcode Command Line Tools，Linux 上通常是 GCC 或 Clang。

本文的 autograd 注册使用 torch.library.register_autograd，因此要求 PyTorch 2.4 或更高版本。若必须兼容 Python 3.9，应使用仍提供 Python 3.9 官方包的 PyTorch 2.4–2.8；PyTorch 2.9 起最低 Python 版本已升为 3.10。

张量检查为什么必须在 C++ 边界做

直接使用 data_ptr 意味着 C++ kernel 自己承担前置条件。至少要检查：

  • device：CPU kernel 不能解引用 CUDA 指针；
  • layout：示例只支持普通 strided 张量，不支持 sparse 等布局；
  • dtype：模板分派必须和真实数据类型一致；
  • shape/size：多输入算子要验证形状、广播规则和索引范围；
  • device index：多 CUDA 输入必须位于预期设备；
  • 空张量：kernel launch 和归约要有明确定义。

失败时使用 TORCH_CHECK，错误会转换成带上下文的 Python RuntimeError。不要依赖 assert：发布构建可能移除它，而且它不是用户输入错误的合适接口。

连续性：检查还是复制

转置、切片后的张量可能不是 contiguous。原始 strides 决定逻辑索引如何映射到内存；把非连续张量当作一维连续数组会读错位置，甚至越界。

Autograd 边界

示例 CPU kernel 用裸指针写新张量。kernel 内部的逐元素乘法不经过 PyTorch dispatcher，因此 autograd 看不到“输出等于输入平方”这条计算图。

本文使用官方推荐的 torch.library.register_autograd 注册 backward：

  • setup_context 保存反向传播所需输入；
  • backward 用 PyTorch 已知的算子表达；
  • 返回值数量必须与 forward 输入数量一致。

不要仅仅因为 forward 输出碰巧带 requires_grad=True 就认为梯度正确。没有注册 autograd 公式的自定义算子，可能给出警告、缺失梯度，或在版本变化后暴露错误。

若 backward 也必须使用自定义 C++/CUDA kernel，应把 backward kernel 同样注册成独立算子，再从 autograd 公式中调用它。需要二阶梯度时，backward 的组成算子也必须可微。

实践建议：

  • 扩展 name 保持稳定，并在不兼容的 schema 变化时改版本后缀；
  • 源码、PyTorch、Python、编译参数或工具链变化后允许重新构建；
  • CI 中缓存目录要把 PyTorch/CUDA/Python/平台纳入 cache key；
  • 用 MAX_JOBS 限制 Ninja 并发，避免编译占满内存；
  • 遇到诡异链接问题时先删除该扩展自己的缓存目录，不要清空整个系统缓存。

JIT 构建适合本地开发，但不适合让每个生产进程在启动时竞争编译。发布场景应预构建 wheel。

编译器与 ABI

传统 LibTorch C++ API 没有承诺跨所有 PyTorch 版本的二进制 ABI 稳定性。稳妥做法是：

  • 用安装当前 PyTorch 后的 CppExtension/load_inline 构建；
  • PyTorch 或 CUDA 大版本升级后重新编译；
  • Linux 上使用与 PyTorch 兼容的 GCC/Clang 和 libstdc++ ABI；
  • macOS 使用 Apple Clang；
  • 不把一台机器上的缓存目录直接复制到不同系统或架构。

CUDA 代码中的关键约束

  • 设备：CUDAGuard 把当前设备切换到输入所在 GPU，作用域结束后恢复。
  • 流：kernel 必须发到 getCurrentCUDAStream()，不能擅自使用默认流，否则会破坏 PyTorch 的异步依赖关系。
  • 同步：正常算子不要调用 cudaDeviceSynchronize()；这会强制全局等待并破坏流水。
  • 错误：C10_CUDA_KERNEL_LAUNCH_CHECK() 检查 launch 错误。异步执行错误仍可能在后续同步点才暴露。
  • 边界：grid-stride loop 对每次访问检查 index < element_count，并限制 block 数避免极端大张量溢出网格配置。
  • 空张量：零元素时不能发射零 block kernel。
  • 连续性：和 CPU 版一样，先显式复制为 contiguous；若要保留 strides，需要重写索引。
  • dtype：示例只覆盖 float32/float64。加入 float16/bfloat16 时要验证累积精度、向量化和体系结构支持，不能只扩大宏分派范围。

macOS 与 CUDA 的边界

Apple 当前平台不提供 NVIDIA CUDA/NVCC。macOS 可以构建并验证本文的 CPU 扩展，但不能本地编译或运行 CUDA kernel；Apple GPU 的 PyTorch 后端是 MPS，它不是 CUDA 的兼容替代。

因此，CUDA 路径必须在配有 NVIDIA GPU、CUDA toolkit 和 CUDA 版 PyTorch 的 Linux/Windows 环境验证。本文在 macOS 环境下只能对 CUDA 源码做静态审阅，不能声称完成了运行验证。

面向生产还缺什么

一个可维护的生产算子通常还应补充：

  • torch.library.register_fake 或 Meta kernel，支持 FakeTensor 与 torch.compile；
  • torch.library.opcheck、torch.autograd.gradcheck 和 CPU/CUDA 对照测试；
  • 非连续、空张量、错误 dtype、不同设备和大尺寸边界测试；
  • autocast 策略与混合精度数值测试；
  • benchmark，且 CUDA 计时前后正确同步；
  • wheel 构建矩阵与明确的 PyTorch/CUDA 兼容范围。

只有 benchmark 证明自定义 kernel 比等价 PyTorch 组合更快时，扩展的维护成本才真正有回报。
